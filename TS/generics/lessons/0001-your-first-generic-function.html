Your First Generic Function

Make a function remember the type its caller gave it.

≈ 30 minutes Read → Recall → Write Win: four compiler-checked generics, no any

You've seen useState<User> and Promise<T> in real code. By the end of this lesson you'll have written the other side of that: a function that declares its own type parameter. That's the first step toward the reusable fetch wrappers and utilities in your mission.

1. The problem: any forgets

Here's a utility you might find in any utils/ folder:

function getFirst(arr: any[]): any {
  return arr[0];
}

const n = getFirst([10, 20, 30]);   // n: any
n.toUpperCase();                    // no error. Crashes at runtime.

The function works on any array, and that part is good. But the caller passed in number[] and got back any. The type information went in and never came out. Switching to unknown is safer, but it still forgets: the caller would have to cast the result back to number.

What we want is a function that works on any type and still remembers which one it got.

“Unlike using any, it’s also just as precise (i.e., it doesn’t lose any information).”
TypeScript Handbook, on generic functions[1]

2. Declare a type parameter

function getFirst<T>(arr: T[]): T | undefined {
  return arr[0];
}

<T> after the function name declares a type parameter. Think of it as a parameter list for types. (arr) receives a value when the function is called. <T> receives a type. Once declared, T can be used anywhere in the signature or the body.

function getFirst<T>(arr: T[]): T | undefined
declares Tuses T (input)uses T (output)
“A function is generic if it declares a type parameter.”
Matt Pocock, Total TypeScript Essentials[2]

The name T is only a convention. <Item> works the same way, and so does the Handbook's <Type>[1]. A longer name often reads better once a function has two or three type parameters.

3. Callers usually don't write the type: inference

const n    = getFirst([10, 20, 30]);     // T = number  → n: number | undefined
const name = getFirst(["Ada", "Linus"]); // T = string  → name: string | undefined

Nobody wrote <number>. TypeScript looked at the value passed for arr, worked out what T must be, and carried that type through to the return type.

“If you don't pass a type argument, TypeScript will attempt to infer it from the function's runtime arguments.”
Total TypeScript Essentials[2]
Try it in VS Code Hover over getFirst at a call site. The tooltip shows the instantiated signature, with T already replaced, e.g. getFirst<number>(arr: number[]): number | undefined. This is the fastest way to debug inference[2].

4. When you must pass the type argument

Inference needs evidence, and that evidence is the arguments. Here's a fetch wrapper of the kind you'd write in a Node service or a Next.js app: 

async function fetchJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return res.json();
}

T appears only in the return type. Nothing about "/api/me" tells TypeScript what the server sends back, so the caller has to say it, by passing a type argument: 

const me = await fetchJson<User>("/api/me");  // me: User

And when you do pass one, it wins. TypeScript checks the arguments against it rather than inferring something else: 

getFirst<string>([1, 2, 3]);
//              ~~~~~~~~~ Error: number is not assignable to string
“If you pass in a type argument, TypeScript will use it as the source of truth.”
Total TypeScript Essentials[2]
Honesty note fetchJson<User> is a promise the caller makes, not one TypeScript checks. If the API actually returns something else, nothing catches it at runtime. Runtime validation (e.g. zod) is a later topic. For now, just know that the type argument is trusted, not verified.

5. Parameter vs argument: now read real code

TermWhere it appearsExample
Type parameterIn a declaration: a placeholderfunction fetchJson<T>(…)
Type argumentAt a use site: the actual typefetchJson<User>(…)

With that split, the code you already see at work reads plainly:

const [user, setUser] = useState<User | null>(null);
// a type ARGUMENT to React's generic useState. Without it, TS would infer
// the state's type from `null` alone, and setUser(someUser) would fail.

const ids: Array<number> = [1, 2, 3];
// a type ARGUMENT to the built-in generic type Array.

async function getUser(): Promise<User> { … }
// a type ARGUMENT to Promise: "this promise resolves to a User".

Every time you've typed <Something> after a name you're using, you were passing a type argument. Starting today, you can also write the declaring side.

6. Recall check

Answer from memory, without scrolling up. A wrong answer here is useful: struggling to recall is what makes it stick. You get one attempt per question.

In function wrap<T>(x: T): T[], what is <T> doing?

<T> right after the function name in a declaration declares a type parameter. Type arguments appear at call sites, like wrap<User>(…).

Given const u: User = …, what is the type of wrap(u)?

TypeScript infers T = User from the argument, then substitutes it into the return type T[]. T itself never leaks out to the caller.

When do you have to write the type argument yourself?

Inference works from the runtime arguments. In fetchJson<T>(url: string): Promise<T>, T only appears in the return type, so there's nothing to infer it from.

In fetchJson<User>("/api/me"), User is a…

At a call site, the type in angle brackets is an argument: the actual type filling the placeholder T.

What does getFirst<string>([1, 2, 3]) do?

An explicit type argument beats inference. T is locked to string, so [1, 2, 3] is checked against string[] and fails. Types never convert values at runtime.

7. Write it: the real exercise

This is the part that builds the skill. The exercise file has type tests written with Expect<Equal<…>>. They fail now and pass once your generics are right, and the TypeScript compiler is the one checking them.

  3. Work through Tasks 1 → 3 (Task 4 is a stretch: two type parameters). No any.
  4. Done when npm run check prints nothing. Only then compare with exercises/solutions/.
If you're stuck Ask yourself three questions: Where do I declare T? Where does the input use it? Where does the output use it? If T appears only in the output, the caller has to pass it.
